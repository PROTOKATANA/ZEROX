## 1 · Derivación del short ID

Tres pasos, y ninguno es el obvio:

```
1. h = SHA256( header(80 B) ‖ nonce(8 B LE) )        ← SHA256 SIMPLE, no doble
2. k0 = h[0..8]  como u64 LE
   k1 = h[8..16] como u64 LE
   s  = SipHash-2-4(k0, k1, txid)
3. shortid = los 6 bytes bajos de s                   ← se tiran los 2 más significativos
```

> "Short transaction IDs are used to represent a transaction without sending a full 256-bit
> hash. They are calculated by:
> # single-SHA256 hashing the block header with the nonce appended (in little-endian)
> # Running SipHash-2-4 with the input being the transaction ID and the keys (k0/k1) set to
> the first two little-endian 64-bit integers from the above hash, respectively.
> # Dropping the 2 most significant bytes from the SipHash output to make it 6 bytes."

**La trampa:** el hash de la cabecera es **single**-SHA256, mientras que el blockhash normal de
Bitcoin es doble. Quien lo implemente "como el blockhash" produce short IDs incompatibles y el
fallo se manifiesta como bloques que no reconstruyen nunca, sin error de protocolo.

En la lista `shortids`, cada ID va **little-endian** en 6 bytes.

**v2 (segwit):** idéntico pero con **wtxid** en vez de txid. Y si la coinbase no va como
prefilled, su short ID se calcula **codificando la tx en formato con testigo**.

**LAGUNA:** BIP 152 **no** define SipHash-2-4 (rondas, constantes, endianness del mensaje).
Remite implícitamente a Aumasson & Bernstein. Hay que ir a esa spec.

## 2 · El nonce: qué ataque compra

> "The resulting 48-bit hash is certainly not large enough to avoid intentionally created
> individual collisions, but **by using the block hash as a key to SipHash, an attacker cannot
> predict what keys will be used** once their transactions are actually included in a relayed
> block. We mix in a per-connection 64-bit nonce to obtain independent short IDs on every
> connection, **so that even block creators cannot control where collisions occur**, and random
> collisions only ever affect a small number of connections at any given time."

El ataque: sin la clave derivada del bloque, un minero podría fabricar transacciones que
colisionen en short ID con las del mempool de los receptores, degradando la propagación de la
red entera. Con la clave dependiendo del bloque —que no existe hasta que existe— no hay
precomputación posible, y el nonce acota el radio de una colisión fortuita.

**Quién elige el nonce y cuándo:**

> "Nodes MAY pick one nonce per block they wish to send, and only build a cmpctblock message
> once for all peers which they wish to send a given block to. Nodes SHOULD NOT use the same
> nonce across multiple different blocks."

⚠️ **AMBIGÜEDAD del propio BIP.** La Justificación dice "per-connection … on every connection";
la norma operativa permite **un nonce por bloque compartido entre todos los peers**. No es una
contradicción normativa (Justification no usa MUST/SHOULD), pero el nonce real es
**por bloque a elección del emisor**, no obligatoriamente por socket. Quien lea solo la
justificación implementará algo más caro de lo que la norma exige.

## 3 · Colisiones: esperadas, y prohibido castigarlas

> "Once the block has been reconstructed, it shall be processed as normal, **keeping in mind
> that short transaction IDs are expected to occasionally collide, and that nodes MUST NOT be
> penalized for such collisions, wherever they appear**."

La cifra que justifica los 48 bits:

> "This means that B = 48 bits short IDs suffice for blocks with up to t = 10000 transactions,
> mempools up to m = 100000 transactions, with failure to reconstruct at most one in
> **F = 281474 blocks**. Since failure to reconstruct just means we fall back to normal
> inv/header based relay, it isn't necessary to avoid such failure completely."

Recuperación: 0 coincidencias o ≥2 coincidencias → el receptor **sabe** que tiene incertidumbre
y pide la tx con `getblocktxn`. El único caso ciego es "exactamente una coincidencia, y es la
equivocada" — probabilidad ínfima, y la salida es **caer al relé normal**, no un error de
consenso.

**LAGUNA:** el BIP **no** dice explícitamente que el receptor deba re-verificar la raíz de
Merkle tras ensamblar con `blocktxn`. Dice "shall be processed as normal", lo que lo implica
por la vía de la validación ordinaria. La obligación textual de comprometer la raíz recae en el
**emisor**, no en el receptor. Para ZEROX esto **debe** hacerse explícito: es lo único que
detecta el caso ciego.

## 4 · Los cuatro mensajes

### `sendcmpct` — 1 byte booleano ‖ u64 LE de versión

> "# The first integer SHALL be interpreted as a boolean (and MUST have a value of either 1 or 0)
> # The second integer SHALL be interpreted as a little-endian version number."

### `cmpctblock` → `HeaderAndShortIDs`

```
header(80 B) ‖ nonce(u64 LE) ‖ CompactSize(n_short) ‖ shortids(6 B c/u, LE)
             ‖ CompactSize(n_pre) ‖ prefilledtxn[]
```

La obligación que más pesa:

> "A node **MUST NOT** send a cmpctblock message without having validated that the header
> properly commits to each transaction in the block, and properly builds on top of the existing,
> fully-validated chain **with a valid proof-of-work** … A node MAY send a cmpctblock before
> validating that each transaction in the block validly spends existing UTXO set entries."

Y:

> "A node MUST NOT send a cmpctblock message unless they are able to respond to a getblocktxn
> message which requests **every** transaction in the block."

### `getblocktxn` → `BlockTransactionsRequest`

```
blockhash(32 B) ‖ CompactSize(n) ‖ indexes[]   ← DIFERENCIALMENTE CODIFICADOS
```

> "A blocktxn response MUST contain **exactly and only** each transaction which is present in the
> appropriate block at the index specified in the getblocktxn indexes list, **in the order
> requested**."

### `blocktxn` → `BlockTransactions`

```
blockhash(32 B) ‖ CompactSize(n) ‖ transactions[]   ← SIN índices: se infieren por orden
```

Algoritmo de reconstrucción, literal:

> "## Taking the prefilledtxn transactions from the original cmpctblock and placing them in the
> marked positions.
> ## For each short transaction ID from the original cmpctblock, in order, find the corresponding
> transaction either from the blocktxn message or from other sources and place it in the **first
> available position** in the block."

### Codificación diferencial — la regla exacta

> "instead of using raw indexes, the number encoded is **the difference between the current index
> and the previous index, minus one**. For example, a first index of 0 implies a real index of 0,
> a second index of 0 thereafter refers to a real index of 1, etc."

Aplica a `indexes` de `getblocktxn` **y** al campo `index` de cada `PrefilledTransaction`.
**No** aplica a `blocktxn`, que no lleva índices.

**LAGUNA:** BIP 152 usa `CompactSize` pero **no lo define** — remite al protocolo P2P de Bitcoin.
Sí exige minimalidad:

> "Only CompactSize encodings which are minimally-encoded … are used by this spec. Any other
> CompactSize encodings are left with **undefined behavior**."

*(ZEROX ya tiene su `CompactSize` minimal en C-ENC-05, así que esta laguna está cubierta en casa.)*

## 5 · Alto y bajo ancho de banda

| | Alto (`sendcmpct` 1) | Bajo (`sendcmpct` 0) |
|---|---|---|
| Anuncio | `cmpctblock` **no solicitado** | `inv`/`headers` (BIP 130) |
| Cuándo | posiblemente **antes de validar el cuerpo** | tras validación completa |
| Coste | RTT×0,5 de latencia, a cambio de subida | un round-trip más |

> "For nodes which have sufficient inbound bandwidth, sending a sendcmpct message with the first
> integer set to 1 **to up to 3 peers** is RECOMMENDED. If possible, it is RECOMMENDED that those
> peers be selected based on their **past performance in providing blocks quickly** … allowing
> nodes to receive blocks which come from those peers in only **0.5*RTT**.
>
> Nodes **MUST NOT** send such sendcmpct messages to **more than three peers**, as it encourages
> wasting outbound bandwidth across the network."

**Negociación de versión** — regla de bloqueo:

> "The encoding version used to send a cmpctblock or blocktxn message or to receive a getblocktxn
> message MUST be the second integer (version number) in the **first sendcmpct message received
> for which a sendcmpct message with the same version number was sent**."

> "Nodes MUST NOT send a request for a MSG_CMPCT_BLOCK object to a peer **before having received
> a sendcmpct message from that peer**."

> "Nodes MUST NOT request a MSG_CMPCT_BLOCK object before having sent **all** sendcmpct messages
> to that peer which they intend to send, as the peer cannot know what version protocol to use."

El truco de sincronización que propone el BIP: mandar todos los `sendcmpct`, luego un `ping`, y
esperar el `pong`.

⚠️ **AMBIGÜEDAD del BIP.** Dice "it does not allow a node to support a specific version in only
one direction (sending or receiving)", pero el resto de la sección describe una negociación con
componentes **direccionales**. Zona de confusión de la propia redacción; se señala, no se resuelve.

## 6 · Prefilled transactions

> "Nodes sending cmpctblock messages **SHOULD limit prefilledtxn to 10KB** of transactions. When
> in doubt, nodes SHOULD only include the coinbase transaction in prefilledtxn."

**LAGUNA que conviene saber:** **no existe** un MUST textual de "incluye siempre la coinbase".
Lo más cercano es una nota condicional de la sección v2 — "though a node normally SHOULD, if a
node does not include (ie must then include the short ID for) the coinbase transaction…".
Que convenga incluirla es evidente por construcción —la coinbase es nueva en cada bloque, así
que jamás está en el mempool de nadie— pero **eso es inferencia, no cita**.

## 7 · Reglas anti-DoS, literales

| Regla | Cita |
|---|---|
| Los `inv` de tipo compacto solo existen en `getdata` | "MSG_CMPCT_BLOCK inv objects **MUST NOT** appear anywhere except for in getdata messages." |
| Validar la cabecera **antes** de emitir | ver §4, `cmpctblock` |
| **No banear** por cuerpo inválido con cabecera válida | "nodes **SHOULD NOT ban** a peer for announcing a new block with a CMPCTBLOCK message that is invalid, but has a valid header." |
| No penalizar colisiones | ver §3 |
| Límite de prefilled | 10 KB, SHOULD |
| No dejar `getdata` sin respuesta | "nodes SHOULD **delay** responding to GETDATA requests for the block until validation has completed, stalling all message processing for the associated peer." |

Y la advertencia para clientes ligeros, que aplica a `zx-lightwalletd`:

> "SPV nodes which implement this spec must consider the implications of **accepting blocks which
> were not validated by the node which provided them**. Especially SPV nodes which allow users to
> select a 'trusted full node' to sync from may wish to avoid implementing this spec in
> high-bandwidth mode."

*(El BIP incluye literalmente, sobre CompactSize no minimal: "should make a best-effort to eat
the sender's cat". Es texto publicado. Significa: comportamiento indefinido, desconexión válida.)*

## 8 · Qué NO es portable a libp2p

El BIP **jamás contempla otro transporte** que el P2P de Bitcoin. Esta frontera es análisis
derivado de qué reglas citan primitivas de Bitcoin, **no** una declaración del BIP:

**Depende del transporte — hay que rediseñarlo:**

- **Toda la negociación de `sendcmpct`** es estado por conexión TCP persistente, con **orden
  total** entre `sendcmpct`, `getdata`, `cmpctblock`, `ping`/`pong`. libp2p multiplexa
  **streams independientes** por protocolo sobre yamux; ese orden total **no está garantizado**
  salvo que se fuerce un único stream lógico por peer. El BIP da por hecho lo que libp2p no da.
- **El modo de bajo ancho de banda entero**, definido en términos de `inv`/`headers`/`getdata`
  con `MSG_CMPCT_BLOCK == 4`. libp2p no tiene esas primitivas.
- El truco de `ping`/`pong` para saber que la negociación acabó.

**Independiente del transporte — portable tal cual:**

- La derivación del short ID (§1): solo bytes.
- Las cuatro estructuras de datos (§4): serializaciones puras.
- El algoritmo de reconstrucción (§4): lógica local sobre datos ya recibidos.
- El cálculo de colisión y la prohibición de penalizar (§3).
- **"Validar la cabecera antes de emitir"** (§7): es una regla sobre el orden causal *interno*
  del nodo, no sobre el canal. Es, además, la más importante de todas.

## Lagunas declaradas

1. **SipHash-2-4** no está en el BIP → spec de Aumasson & Bernstein.
2. **CompactSize** no está en el BIP → protocolo P2P de Bitcoin. *(ZEROX ya lo tiene: C-ENC-05.)*
3. **No hay MUST** de incluir la coinbase en prefilled; es inferencia de diseño.
4. **No se especifica** cómo detecta el receptor un fallo residual de reconstrucción tras
   `blocktxn`. Para ZEROX hay que hacerlo explícito.
5. El BIP **no dice nada** sobre libp2p, streams multiplexados ni mensajería sin conexión
   persistente. Toda la adaptación es terreno propio.
